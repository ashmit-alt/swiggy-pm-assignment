AI Trip Planner

    Goal of the system

    Turn user intent into a personalised and bookable trip.

    From a few trip facts and a free-text wish, the system builds a day-by-day plan that fits the traveller’s constraints and taste, uses only real, available inventory, and can be booked as it stands, with no re-planning by hand.

    User inputs

    Output

    A personalised, bookable itinerary

    • Cities, order and dates
    • Stays and day plans
    • Transport between places
    • Live options, ready to book

    What is a bookable itinerary?

    It resolves every decision needed to transact the trip: where to go, when to go, where to stay, what to do and how to move between places.

    1. 1Trip structure

      Cities · order · dates · duration

      Tokyo 2 nights → Kanazawa 2 → Kyoto 2
      28 Apr – 4 May

    2. 2Trip execution

      Hotels · activities · timings · routes

      Ryokan in Gion · Fushimi Inari at 07:00
      Shinkansen to Kanazawa, day 3, 10:24

    3. 3Bookable inventory

      Flights · hotels · trains · activities · transfers

      BLR → Tokyo via Bangkok · 3 hotels
      2 trains · KIX transfer, each with a live price

    A valid output must be

    RealNo made-up places, prices or availability
    FeasibleConstraints, timings and routes work
    ConsistentEvery part of the trip fits together
    MeasurableQuality can be scored objectively
    Takeaway

    The output is not a suggestion. It is a trip that can be booked as is.

    How does the AI read the repository?

    Exact names and IDs get near misses

    1. Nishi Chaya→Higashi Chaya0.95wrong district
    2. Flight SQ 511→SQ 5170.97wrong flight
    3. Hotel H-20418→H-204810.96wrong hotel

    Embeddings match meaning, not exact strings. A name, flight number or booking ID that is one character off still scores as a top match.

    Query“vegetarian, old Japan, no crowds”

    1. Ramen alley0.91not veg
    2. Kinkaku-ji0.89peak crowds
    3. Machiya café0.88closed

    Similar is not the same as correct, and nothing flags it.

    veg = yes AND stairs = low

      One run · the Japan trip

      1. 1
        Understand

        The conversational agent writes the trip state and asks one question: steps for the knee.

      2. 2
        Draft

        Golden Week, so favour Kanazawa, early starts and few moves. Drafts plans A, B and C.

      3. 3
        Critique

        C: no Takayama rooms on 1 May. B, day 5: 4.6 km. All plans: ₹3.15 L against ₹2.5 L.

      4. 4
        Revise or ask

        Drops C, fixes B with a taxi. The budget is a hard rule, so it asks: ₹3.2 L, or 10–16 May?

      5. 5
        Present

        Every hard critic passes. Plan A, 0.46, ₹3.15 L, every claim cited.

      North Star

      Bookable trip rate

      The share of planning sessions that end with the traveller booking at least one item from the itinerary.

      It only goes up when the plan is real, fits the traveller and can actually be booked: the goal from the Goals tab.

      Plan quality

      Is it correct?

      • Hard-rule pass rate↑ Target 100%

        Plans shown with zero broken hard rules: dates, diet, walking, budget.

      • Fact accuracy↑ Target ≥ 99%

        Places, prices and times that still match live data at booking.

      • Price drift↓ Target < 2%

        Gap between the price we quoted and the price at booking.

      Traveller value

      Do they like it?

      • Plan acceptance↑ Higher is better

        Sessions where the first plan shown is kept, with few or no edits.

      • Edits per plan↓ Fewer is better

        Changes the traveller asks for before booking.

      • Rating / NPS↑ Higher is better

        How travellers rate the plan after the trip.

      Efficiency

      Can we run it?

      • Time to first plan↓ Target < 10 s

        Seconds from the request to a full itinerary.

      • Cost per plan↓ Lower is better

        Model and API cost for each itinerary.

      • Questions asked↓ Target 1–2

        Clarifying questions per session: low, but not zero.

      Guardrails · must never get worse

      • No booking fails because of availability we got wrong
      • Hard constraints like diet and mobility are never broken
      • Re-plans change only what they must

      How we measure it: about 20 hand-built test trips re-run offline on every change, plus live tracking in production with A/B tests for big changes.
